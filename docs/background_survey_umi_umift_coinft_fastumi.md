# UMI、UMI-FT、CoinFT 与 Fast-UMI 背景调查

> 本文用于汇报中的“技术背景与硬件选型依据”部分。
>
> 调查对象包括 Stanford UMI、UMI-FT、CoinFT 和 Fast-UMI 的公开项目页、论文、GitHub 代码与数据处理脚本。
>
> 文中将明确区分：
>
> - 官方项目已经明确说明的事实。
> - 根据公开实现和本项目需求做出的工程归纳。
> - 当前项目已经实现的内容与后续规划。

## 1. 先给结论

我们选择 UMI/UMI-FT 作为数据采集基础，并不是因为它只提供了一个手持夹爪，而是因为它解决了机器人数据采集中的三个核心问题：

1. **不需要让人在真实机器人旁边长时间遥操作。**
2. **不把数据绑定到某一台机器人的关节空间。**
3. **可以同时获得视觉、末端动作、夹爪状态和接触力觉。**

在此基础上，我们选择 iPhone 和 CoinFT，原因分别是：

- iPhone 可以把 RGB、Depth、ARKit 6DoF 位姿和相机标定信息集成在一个移动设备中。
- CoinFT 可以安装在两个夹爪指端，以很小的体积和重量获取左右指尖的六维力/力矩。
- 两者结合后，示教数据不再只有“看到了什么”和“夹爪怎么动”，还包含“接触时施加了什么力”。

当前项目的整体设计可以概括为：

```text
UMI 的本体无关示教接口
    + UMI-FT 的指尖六维力觉
    + iPhone 的 RGB / Depth / ARKit 位姿
    + D435i 的固定全局视角
    + 笔记本端的时间同步与数据工程
    -> 多模态、可追溯、可跨机器人使用的示教数据
```

### 1.1 硬件选型真正要回答的四个问题

“iPhone 能记录 RGB、CoinFT 能记录力”只是功能描述，不足以构成选型理由。真正的问题是：在手持示教器上，哪种方案能同时满足下面四点。

| 约束 | 如果处理不好会怎样 | 本项目的选择 |
| --- | --- | --- |
| 质量与惯量 | 设备重、重心远离手腕，示教动作变慢且不自然 | UMI 的被动夹爪结构 + 2 g 级 CoinFT + 手机一体化传感器 |
| 成本与可复制性 | 只能做一两套原型，无法积累足够多、足够多样的 demo | 3D 打印 UMI 结构、常见 iPhone、低 BOM CoinFT |
| 传感器集成 | 多个相机、追踪器、F/T 和同步板卡使装置脆弱 | iPhone 合并 RGB/Depth/pose，Teensy 只做 CoinFT 低层转发 |
| 数据语义 | 模型要从混乱的绝对坐标和视觉噪声中猜动作、接触和目标 | 工具相对轨迹、夹爪状态、左右 wrench、独立 timestamp 和 contact-aware 标签 |

因此，UMI-FT 不是“把很多传感器堆到夹爪上”，而是围绕**可批量采集、可解释、可拟合、可部署**四个目标做的系统级取舍。

### 1.2 为什么 UMI 的低成本不是一句口号

UMI 的机械主体是可 3D 打印、主要依赖被动机械结构的手持平行夹爪。它不需要在示教阶段配一台机器人、主从臂、机器人控制柜或关节编码器链路。对每增加一个采集节点而言，主要增量是打印件、紧固件、相机/手机和传感器，而不是另一套高价值机器人平台。

这件事直接影响数据质量，而不只是预算：同样的采集预算能获得更多示教器、更多场景、更多操作者和更多失败恢复样本。对于行为克隆，示教分布的广度通常比把少量实验室轨迹测得极端精确更有价值。

### 1.3 为什么“本体无关”不是“完全不需要适配”

UMI 的数据不绑定某个机器人的关节角，因此能跨 6DoF、7DoF 等不同机械臂复用；但它并不自动消除所有本体差异。部署到特定机器人时仍需要：

- 工具/TCP 外参。
- 目标机器人工作空间、速度、关节和碰撞约束。
- 目标夹爪开合范围和命令接口。
- 机器人端相机与示教端相近的观测口径。

UMI 的价值是把这些差异压缩到**执行适配层**，而不是让它们污染每一次人类示教的数据。

## 2. 为什么需要 UMI 这类数据采集接口

### 2.1 传统机器人示教的主要问题

直接用机器人采集示教，通常需要：

- 让示教者在机器人工作空间内操作。
- 使用 SpaceMouse、VR、主从机械臂或其他遥操作设备。
- 同时处理机器人安全、碰撞、关节限位和设备故障。
- 为每一台机器人配置一套采集和控制接口。

这会带来两个问题。

第一，数据采集环境被限制在实验室中，难以收集自然、快速、双臂和长时序的操作。第二，数据通常以机器人关节角或某一特定机械臂的控制命令表达，换一台机器人就需要重新采集或重新标注。

### 2.2 UMI 的基本思路

UMI 的思路是把“示教”和“机器人执行”拆开：

```text
人手拿着一个带传感器的夹爪完成任务
    -> 记录视觉和工具运动
    -> 得到与机器人关节结构无关的末端动作数据
    -> 在目标机器人上使用相同或相似的工具观测接口执行
```

它不是把人手动作简单录成普通视频，而是设计一个**可测量的手持操作接口**。手持夹爪提供一个明确的末端工具，摄像头记录工具附近的观察，视觉惯性系统恢复工具运动，夹爪开合由视觉 marker 或夹爪状态估计得到。

### 2.3 UMI 相比普通人手视频的关键优势

普通视频通常缺少明确的 action。视频里可以看到人手移动，但不一定知道：

- 末端在三维空间中移动了多少。
- 旋转了多少。
- 夹爪什么时候闭合。
- 动作发生时的速度和时序是什么。

UMI 通过手持工具和相机轨迹把这些信息显式记录下来，因此数据更接近机器人策略所需要的 observation-action trajectory。

### 2.4 UMI 试图减小的不是一个“视觉差异”，而是两个 gap

#### Action gap

示教者的动作要能够转换为机器人的末端动作。UMI 使用工具末端的 6DoF 轨迹，而不是人的关节角，因此机器人可以在执行端通过自己的逆运动学重新求解关节动作。

#### Observation gap

训练时看到的画面和执行时看到的画面应该尽量一致。UMI 因此把相机安装在手持工具上，部署到机器人时也让相机跟随机器人末端，保持相似的视角。

## 3. UMI 的硬件设计与实现原理

### 3.1 原始 UMI 的硬件思路

原始 UMI 使用一个手持式平行夹爪，并在腕部安装 GoPro。公开论文和项目页强调了几个硬件设计目标：

- 夹爪要便于人手操作。
- 腕部相机要提供稳定的第一视角观察。
- 鱼眼镜头扩大视野，减少局部视角造成的遮挡。
- 夹爪两侧的镜面提供额外的隐式立体视觉信息。
- GoPro 自带 IMU，与视觉 SLAM 结合后恢复快速运动中的 6DoF 轨迹。

原始 UMI 的核心视觉链路是：

```text
GoPro 视频 + GoPro IMU
    -> 相机/视觉惯性 SLAM
    -> 相机轨迹
    -> 固定外参转换为工具/TCP轨迹
    -> 机器人末端动作
```

### 3.2 原始 UMI 为什么可以支持动态和双臂任务

如果只有低频或不稳定的手部跟踪，示教数据通常只能支持慢速、准静态的抓取和放置。UMI 重点解决了：

- 快速运动中的 6DoF 轨迹恢复。
- 夹爪视角和动作轨迹的时间对应。
- 双臂设备之间的同步。
- 训练时和部署时的观察、推理、执行延迟差异。

原始 UMI 还提出了两个重要的软件接口设计：

1. **相对轨迹动作表示**：策略学习相对于当前末端状态的运动，降低对绝对世界坐标和精确全局标定的依赖。
2. **推理时延匹配**：训练数据中采集和动作记录几乎同时发生，但机器人执行时会有相机、传输、推理和执行延迟，因此部署时需要把动作和观测按延迟重新对齐。

### 3.3 原始 UMI 的局限

公开论文也说明了原始路线的限制：

- 视觉 SLAM 依赖场景纹理，纯白墙等低纹理环境更困难。
- wrist-mounted camera 的视野容易被手和物体遮挡。
- 采集装置相对人手仍有重量和体积。
- 下游机器人的运动学限制在采集时通常未知，因此需要后处理筛选不可执行轨迹。

这些限制正是我们增加 D435i、保留 depth、强化时间戳和数据质量检查的背景原因。

## 4. 为什么 UMI-FT 要加入 CoinFT

### 4.1 仅有视觉和位姿还不够

很多任务的关键不是“把夹爪移动到某个位置”，而是：

- 接触表面时施加多大的力。
- 插入、擦拭、旋拧时怎样调节接触力。
- 两个指尖之间的夹持力是否足够。
- 什么时候发生碰撞、卡住或滑动。

仅使用 RGB、Depth 和末端位姿，模型可以学习运动轨迹，但很难直接知道操作过程中接触力的变化。

### 4.2 CoinFT 的核心定位

CoinFT 是一种硬件体积很小的电容式六轴力/力矩传感器，目标是把六维力觉放到传统商业 F/T 传感器难以安装的位置，尤其是夹爪指端。

公开资料中给出的主要特点包括：

- 约 `20 mm` 直径、约 `3 mm` 厚。
- 单个传感器约 `2 g`。
- 每个传感器输出三轴力和三轴力矩。
- 采用电容式感知，原始信号经过非线性模型映射为六维 wrench。
- UMI-FT 论文中给出的 BOM 成本约为每个传感器 `10 美元`。
- 相比昂贵、笨重、易损的商用腕部 F/T 传感器，更适合大规模部署和手持采集。

### 4.2.1 为什么不直接使用商用六维力/力矩传感器

这里的结论不应说成“商用 F/T 完全无法安装”。在机器人腕部安装商用 F/T 是成熟方案；问题在于它不适合这类**双指、手持、可规模复制**的示教器。

| 维度 | 商用腕部六维 F/T | CoinFT 指端方案 | 对手持 UMI 的影响 |
| --- | --- | --- | --- |
| 安装位置 | 通常位于机械臂法兰或工具腕部 | 可布置到左右指端 | 只有指端方案能区分左右接触与内部夹持力 |
| 质量与体积 | 传感器本体、法兰转接件、线缆和采集接口通常远大于 2 g 级指端传感器 | 单个 CoinFT 约 2 g、20 mm 直径、3 mm 厚 | 质量和重心决定人能否自然、快速地长期示教 |
| 供电与数据链路 | 通常需要专用放大/DAQ、屏蔽线缆、稳定供电或工业接口 | 两个传感器可由轻量 MCU/串口链路统一转发 | 手持装置不必背负复杂电子和大束线缆 |
| 成本 | 商用六维 F/T 及其接口通常是高价值工业部件 | UMI-FT 论文报告每个 CoinFT 的 BOM 约 10 美元 | 低成本才允许损坏替换、复制多套和扩大数据规模 |
| 可观测性 | 主要得到工具整体受力 | 分别得到左指和右指 wrench | 可同时表达外部接触、左右不均衡和夹持力 |

所以选 CoinFT 并不只是因为“它能测六维力”，而是因为它把六维力觉从腕部搬到了手持设备真正需要的指端位置，并把质量、供电、成本和可替换性控制在可规模采集的范围内。

### 4.2.2 CoinFT 的本质：它直接测的是电信号，不是力

这一点必须在汇报中说清楚。CoinFT 不是一个把牛顿和牛顿米直接读出来的理想力计。

```text
外力/力矩
    -> 弹性介电结构发生形变
    -> 电场分布和电容通道发生变化
    -> 12 路原始电信号 C1...C12
    -> 每颗传感器自己的学习式标定模型 f_theta
    -> 估计 wrench [Fx,Fy,Fz,Mx,My,Mz]
```

它真正直接观测的是多个电容通道随形变而发生的变化；六维 wrench 是一个经过标定的**回归估计值**。在 UMI-FT 的公开实现中，具体是：

```text
raw_12ch
    -> tare 去除初始偏置
    -> 用 norm.json 做输入归一化
    -> ONNX MLP 推理
    -> 输出反归一化
    -> 6D wrench
```

论文中使用五个隐藏全连接层的 MLP；每个 CoinFT 都需要自己的归一化参数和模型。也就是说：

- `Fx...Mz` 是通过小型神经网络从电场/电容变化中“推断”出来的力觉，不是传感器原生直接给出的物理量。
- 模型只应在标定时覆盖的载荷范围、安装结构和温漂条件附近使用。
- 传感器换位置、换指端结构或出现机械损伤后，必须重新标定或至少重新验证。

这不意味着 CoinFT 的输出“不可信”。所有传感器都需要从某种原始物理量映射到工程单位；CoinFT 的特点是这个映射明显非线性，因此把系统辨识交给了小模型，而不是使用固定线性标定矩阵。

### 4.3 为什么是“每个指头一个”，而不是腕部一个

腕部 F/T 传感器测到的是经过夹爪结构传递后的合力。它很难直接区分：

- 外部环境作用在整个工具上的力。
- 左指和右指分别施加的力。
- 夹持物体所需的内部 grasp force。

每个指头安装一个 CoinFT，可以保留左右独立的六维力觉：

```text
left finger  -> [Fx, Fy, Fz, Mx, My, Mz]
right finger -> [Fx, Fy, Fz, Mx, My, Mz]
```

这样既可以计算工具受到的外部合力，也可以估计夹爪的内部夹持力。

UMI-FT 论文的控制方式是：

1. 将左右传感器的 wrench 变换到机器人 tool/TCP 坐标系。
2. 把左右 wrench 合成为工具层面的外部力觉反馈。
3. 沿夹持方向计算或估计 grasp force。
4. 分别用于腕部柔顺控制和夹爪夹持力控制。

### 4.4 CoinFT 相比传统 tactile sensor 的优势

CoinFT 并不是高分辨率的视觉触觉图像传感器，而是更直接的六维力/力矩测量。它的优势是：

- 数据语义清晰，直接对应力和力矩。
- 可以通过商用 F/T 传感器进行标定，建立跨设备的一致测量尺度。
- 只要载荷路径经过传感器，就可以测到沿指体不同位置传递的力，不要求整块接触区域都覆盖传感器。
- 输出可以经过坐标变换转换到任意目标 tool frame，便于接入标准柔顺控制器。

### 4.5 CoinFT 的实现和标定原理

CoinFT 的原始电容信号和真实力/力矩之间具有明显非线性，因此不能简单使用一个线性矩阵完成标定。UMI-FT 采用如下流程：

```text
CoinFT 12路原始电容/通道数据
    -> 去 tare offset
    -> 输入归一化
    -> MLP/ONNX 非线性回归
    -> 输出归一化逆变换
    -> 六维 wrench [Fx,Fy,Fz,Mx,My,Mz]
```

标定时，将完整的 UMI-FT 指端结构安装好，并使用 ATI Gamma 等商用 F/T 传感器作为参考。在多个方向施加随机力和力矩，使模型学习“实际安装结构”下的原始信号到六维力觉的映射。

这说明一个重要工程原则：

> CoinFT 不能只单独标定传感器本体，还要在最终夹爪结构和安装位置下进行系统级标定。

更严格地说，标定集定义了这个“力觉估计器”的有效边界。对于汇报，推荐使用“经参考 F/T 标定的六维 wrench 估计”这一表述，而不是无条件地称它为“真实力的直接测量”。

### 4.6 CoinFT 的工程风险

CoinFT 不是没有限制：

- 电容信号和力觉之间非线性较强。
- 传感器的拉伸承受能力低于压缩承受能力。
- 指端到传感器之间的力臂过长时，弯矩可能造成分层或损伤。
- 传感器安装位置和夹爪结构会影响标定结果。

因此 UMI-FT 将传感器尽量靠近指尖，并让主要夹持载荷以压缩方式作用在传感器上。

## 5. 为什么 UMI-FT 选择 iPhone 15 Pro

### 5.1 官方硬件事实

UMI-FT 论文明确描述的硬件是：

- iPhone 15 Pro 刚性安装在 UMI-FT 结构上。
- 手机有约 15° 倾角，用于更好地看到手指工作区域和 ArUco marker。
- 主 RGB 和 pose 由 ARKit 提供，论文中记录为约 60 Hz。
- ultrawide RGB 约 10 Hz。
- depth 约 30 Hz。
- 同一个 iPhone 设备同时提供 RGB、Depth、pose 和相机参数。

### 5.2 Apple/iPhone 的真正价值

公开论文没有把“选择 Apple”表述为一个孤立的品牌决策，但从 ARKit 和硬件集成能力来看，iPhone 主要提供了下面几个系统级优点。

首先，它是一个很容易获得、很容易替换、也很容易复制的软件定义传感器节点。相比自己组合广角相机、深度相机、IMU、视觉惯性里程计板卡、计算单元和同步板卡，iPhone 将这些能力封装在同一硬件和 SDK 中。对需要不断迭代采集 App 的研究项目而言，iOS/ARKit 的开发门槛和调试成本也显著低于从零维护一条视觉惯性 SLAM 工程链。

#### 1. 把相机、深度和位姿集成到同一设备

如果 RGB 相机、深度相机和外部跟踪器分别安装，就需要处理：

- 三套设备时钟。
- 三个数据传输链路。
- 不同设备之间的外参。
- RGB、Depth 和 pose 的帧对应关系。

iPhone/ARKit 可以在设备内部把主 RGB、Depth、相机内参和 6DoF pose 组织起来，显著减少采集端的系统复杂度。

#### 2. ARKit 提供成熟的视觉惯性跟踪

UMI 的核心不是只拍视频，而是要获得可以转成 action 的相机/工具轨迹。ARKit 将相机图像、惯性传感器和空间跟踪封装成统一的 pose 输出，适合构建移动的手持采集节点。

#### 3. 适合在手持设备上完成局部视觉任务

UMI-FT 需要同时看到：

- 操作物体。
- 夹爪指端。
- 两个 ArUco marker。

因此 iPhone 不是简单固定在夹爪上拍一个前视视频，而是以特定倾角安装，使它能兼顾操作场景和夹爪开合测量。

#### 4. 统一设备便于低成本复制

商用手机的相机、深度和惯性硬件已经集成，复制一套采集节点时不需要重新设计多传感器同步板卡。

#### 5.2.1 iPhone 的成本优势是“减少系统成本”，不只是手机价格

手机本身并不一定比一台普通工业相机便宜，但它替代的是一组设备和集成工作：

```text
广角 RGB 相机
    + 深度相机
    + IMU
    + 视觉惯性定位软件
    + 相机内参管理
    + 多模态 timestamp 对齐
    + 设备端预览和录制界面
```

在 iPhone/ARKit 路线中，这些能力以统一 API 和同一设备时钟提供。对 UMI-FT 这种需要多套采集器、并且未来可能由不同操作者使用的系统，这通常比“分别买到每个硬件”的成本更关键：它降低了装配、标定、故障定位和软件维护成本。

当然，iPhone 不是无代价选择。它依赖 Apple 硬件和 ARKit 行为，私有 ultrawide API 也可能受 iOS 版本影响；因此当前项目保留了能力探测、原始数据落盘和笔记本端对齐，而不把整个系统建立在一个不可验证的手机输出上。

### 5.3 iPhone 与原始 UMI GoPro 的关系

这里需要在汇报中讲清楚演化关系：

| 系统 | 主要视觉/位姿路线 | 设计重点 |
| --- | --- | --- |
| 原始 UMI | GoPro 鱼眼 RGB + IMU + SLAM | 大视野、快速运动、跨机器人观察一致性 |
| UMI-FT 论文硬件 | iPhone 15 Pro 的 RGB/Depth/ARKit pose + 双 CoinFT | 多模态采集、指尖力觉、柔顺操作 |
| Fast-UMI | GoPro/相机 + RealSense T265 等商用跟踪硬件 | 直接获得末端位姿，减少 SLAM 工程复杂度 |
| 当前项目 | iPhone RGB/Depth/ARKit pose + CoinFT + D435i | 继承 UMI-FT 多模态思路，并增加固定全局 RGB-D |

UMI-FT 开源仓库中的部分采集说明仍然保留 GoPro 时间同步和 GoPro demo 文件夹。从代码和论文的对应关系看，这更像是原始 UMI 工作流与 UMI-FT iPhone 工作流并存的继承/过渡实现；论文中的 UMI-FT 硬件描述则明确写的是 iPhone 15 Pro。

## 6. Fast-UMI 的思路和它带来的启发

### 6.1 Fast-UMI 试图解决什么问题

Fast-UMI 的公开摘要将目标概括为：

- 可扩展。
- 硬件无关。
- 手持设备采集数据。
- 机器人端使用独立的安装设备进行策略执行。
- 直接使用商用硬件获得末端位姿，减少复杂 SLAM 部署。

它把系统明确拆成两部分：

```text
handheld device for human data collection
    -> standardized trajectory / observation data

robot-mounted device for policy inference
    -> target robot execution
```

### 6.2 Fast-UMI 的典型实现链路

公开仓库中可以看到一条比较直接的工程路线：

```text
RealSense T265 odometry
    -> T265 到 TCP 的固定 offset
    -> TCP trajectory
    -> 可选 IK 转换为机器人关节轨迹
    -> HDF5/Zarr 等训练格式
```

夹爪宽度则通过夹爪上的 ArUco marker 估计：

```text
marker pixel distance
    -> 标定的最小/最大像素距离
    -> 实际 gripper width
```

### 6.3 Fast-UMI 的优点

- 直接使用商用跟踪硬件，减少自行维护 SLAM 的成本。
- 手持设备与机器人执行端解耦。
- 可以输出 TCP 数据，也可以进一步计算机器人关节数据。
- 采用 HDF5/Zarr 等结构化数据格式，便于训练和转换。
- 更强调“快速部署”和“硬件无关”的工程可用性。

### 6.4 Fast-UMI 和原始 UMI 的差异

两者都使用手持式采集器，但重点不同：

- 原始 UMI 更强调相机、IMU、SLAM、相对轨迹和观察视角一致性。
- Fast-UMI 更强调使用成熟商用定位设备直接获得末端轨迹，降低软件和标定门槛。
- UMI-FT 在原始 UMI 的基础上加入了每指一个 CoinFT，重点解决力觉和柔顺操作。

对于当前项目，Fast-UMI 的启发是：

> 采集端输出应该尽量是标准的末端动作和多模态 observation，而不是写死某个机器人品牌的关节接口。

## 7. UMI-FT 数据采集和对齐是如何实现的

### 7.1 采集的模态

UMI-FT 的一个 episode 通常包括：

```text
iPhone / camera:
  RGB
  ultrawide RGB
  depth
  camera pose
  gripper width

CoinFT:
  left 6D wrench
  right 6D wrench
  raw sensor channels
```

各模态采样率不相同。论文中给出的典型频率是：

- 主 RGB + pose：约 60 Hz。
- ultrawide RGB：约 10 Hz。
- depth：约 30 Hz。
- 每个 CoinFT：约 360 Hz。

### 7.2 采集顺序

公开 UMI-FT Data README 的流程大致是：

1. 在 iPhone App 中设置 session name。
2. 进行 GoPro/iPhone 或多设备时间同步步骤。
3. 录制夹爪开合标定视频。
4. 启动 CoinFT 采集脚本。
5. 在 iPhone App 上开始和结束 demo episode。
6. 导出 iPhone/GoPro 文件，与 CoinFT CSV 放到同一个 session 目录。
7. 进行多模态后处理并生成 Zarr。

这体现了一个重要原则：

> 先完整记录原始数据，再根据 episode 边界做后处理对齐，而不是让所有设备必须在同一瞬间启动和停止。

### 7.3 CoinFT 的时间戳

公开 UMI-FT 代码中的 CoinFT 采集脚本：

- 读取两路 CoinFT 的二进制串口包。
- 每个传感器保留 12 路原始通道。
- 对 raw 数据做 tare。
- 使用各自的归一化参数和 ONNX 模型输出六维 wrench。
- 使用 NTP 或网络时间建立时间基准。
- 左右传感器分别保存 CSV。

典型数据包结构是：

```text
header + left 12 x uint16 + right 12 x uint16
```

### 7.4 多模态时间对齐

UMI-FT 的数据处理不会把所有数据简单按数组下标一一对应，而是使用每一路自己的 timestamp：

```text
RGB timestamp
pose timestamp
depth timestamp
gripper timestamp
left wrench timestamp
right wrench timestamp
```

后处理主要包含以下步骤：

#### 1. 找到同一个 demo 的时间区间

将 iPhone pose/camera 数据和 CoinFT 数据按文件名、session 和时间范围匹配。如果两个数据流时间区间没有交集，则认为该 demo 无法正确对齐。

#### 2. 以主视觉/pose 轨迹作为 episode 参考

图像、pose 和 gripper 数据通常具有相同的主帧索引；CoinFT 保留更高频的独立时间序列。

#### 3. 将夹爪宽度插值到 CoinFT 时间点

源码中使用时间插值：

```text
gripper_width_at_ft_time
    = interpolate(gripper_width, gripper_timestamp, ft_timestamp)
```

这是因为 CoinFT 频率高于夹爪宽度/pose 频率，而力矩坐标变换需要知道每个 CoinFT 时刻的夹爪开合宽度。

#### 4. 进行 CoinFT 坐标到 TCP 坐标的变换

传感器测到的是 sensor frame 下的 wrench。根据当前夹爪宽度和 CoinFT 到 TCP 的几何变换，对左右 wrench 分别做空间力变换：

```text
sensor-frame wrench
    -> CoinFT 到 TCP 的刚体变换
    -> adjoint(wrench) 变换
    -> left/right TCP wrench
    -> 可选拼接或合成为工具层 wrench
```

力/力矩不能简单只旋转三个力和三个力矩，因为参考点发生变化时还会产生力矩项。

#### 5. 保留独立时间轴和独立长度

UMI-FT 的 Zarr 数据中，RGB/pose/gripper 和 wrench 的第一维长度可以不同：

```text
T = 主视觉/pose/gripper 样本数
F = 高频 CoinFT 样本数
T != F 是正常的
```

### 7.5 UMI-FT Zarr 数据结构

官方示例采用 episode 分组：

```text
acp_replay_buffer_gripper.zarr/
  data/
    episode_0/
      rgb_0
      depth_0
      ts_pose_fb_0
      gripper_0
      wrench_left_0
      wrench_right_0
      wrench_concat_0
      wrench_left_coinft_0
      wrench_right_coinft_0
      *_time_stamps_0
  meta/
    episode_*_len
```

主要字段含义：

| 字段 | 含义 |
| --- | --- |
| `rgb_0` | 手持夹爪的第一视角 RGB |
| `depth_0` | 深度图 |
| `ts_pose_fb_0` | 反馈/SLAM 工具位姿，通常为位置加单位四元数 |
| `gripper_0` | 连续夹爪宽度 |
| `wrench_left_0` | 左指转换到 tool/TCP frame 的六维 wrench |
| `wrench_right_0` | 右指转换到 tool/TCP frame 的六维 wrench |
| `wrench_concat_0` | 左右 wrench 拼接 |
| `*_coinft_0` | 保留传感器原坐标系下的数据 |
| `*_time_stamps_0` | 对应模态自己的时间戳 |

### 7.6 为什么不把所有数据重采样成一个频率

简单重采样会丢失高频力觉，也可能让低频深度和高频视觉产生伪精度。更合理的做法是：

- 采集阶段保留原始采样率。
- 每个模态保留原始或规范化 timestamp。
- 在训练 sampler 或对齐阶段按时间查询最近样本或插值结果。
- 对缺帧、时间跨度过大和无效样本显式记录 validity。

这也是当前项目采用 `raw -> normalized -> aligned -> export` 分层的依据。

### 7.7 UMI 数据为什么比“普通视频 + 绝对位姿”更容易被策略拟合

这不是因为 UMI 让视觉问题消失，而是因为它把策略要学习的关系改写成了一个更简单、更稳定的局部问题。

#### 1. 观察、动作和接触共享同一个工具坐标语义

腕部/夹爪相机看到的是末端即将接触的局部区域；位姿是同一个末端的运动；左右 wrench 又是同一对手指的接触反馈。它们不是松散拼接的三路数据，而是围绕一个工具/TCP 组织的闭环：

```text
rgb / depth:       工具此刻看见什么
T_world_tool:      工具此刻在哪里、朝向哪里
gripper width:     工具是否准备抓取
left/right wrench: 工具是否已经接触、如何受力
future relative pose: 下一步应朝哪里移动
```

相机与动作共视角尤其重要。一个固定第三人称相机需要先判断“画面中的哪一个点对应机器人末端”，而 UMI 的相机天然跟随末端，目标通常出现在动作方向的前方。这把视觉到动作的映射限制在一个更局部、更一致的坐标关系中。

#### 2. 绝对世界坐标被改写为当前工具坐标系中的相对运动

本地 UMI-FT 训练代码并不直接使用全局 `T_world_tool` 作为观测或标签。对每个训练样本，它取观测窗口最后一帧的工具位姿 `T_ref`，然后把观测窗口和未来动作窗口都改写为：

```text
T_relative(t) = inverse(T_ref) @ T_world_tool(t)
```

这意味着网络学习的不是：

```text
“世界坐标 (1.37, -0.42, 0.18) 处应该做什么？”
```

而是：

```text
“从我当前夹爪向前 6 cm、向左 2 cm、旋转若干角度的位置，应该如何移动？”
```

这样消除了每次示教 reset origin、桌子摆放、机器人 base 安装和 SLAM 全局漂移带来的大部分无关变化。对模型而言，目标变量范围更小、分布更集中，数据量需求也更合理。

本地实现还会把 wrench 用相同参考坐标变换到局部 frame，避免“同样的接触力在不同世界朝向下具有不同坐标分量”的问题。

#### 3. 接触事件给“抓取目标”提供了不依赖视觉识别的物理锚点

普通视觉策略要从有遮挡、反光、相似物体和光照变化中判断“我是否真正碰到目标”。UMI-FT 增加了更直接的物理证据：

```text
接近阶段：夹爪张开，左右指力接近零，未来相对位姿指向前方目标
接触阶段：夹爪闭合或持续推进，左右 wrench 出现显著变化
抓取阶段：两侧沿夹持轴的接触力同时存在，形成 grasp-force 信号
操作阶段：外部 wrench 与相对位移共同反映摩擦、插入、擦拭或卡住
```

因此，**接触前若干帧的 future relative pose**天然是“朝哪个局部空间位置移动，最终将发生接触/抓取”的监督。结合之后发生的夹爪闭合和力上升，模型可以学习到目标的相对方向和距离，即使图像中目标边缘不够可靠。

这应准确称为：

> 力觉和时序动作使目标接触位置成为一个可学习的隐变量或物理锚点。

它不是当前代码显式生成的 `object_position` 真值标签。代码没有从力和反向运动直接写出一个“物体三维坐标”；它提供的是更可靠的时序监督，让策略无需只依赖单帧视觉检测器去猜目标。

#### 4. 左右指力把“是否抓到”和“抓得是否合适”分开了

本地 UMI-FT 数据转换代码将左右 TCP frame 下的夹持方向分量做符号对齐后求平均：

```text
grasp_force = (-F_left_x + F_right_x) / 2
```

这个量和 gripper width 一起区分了几个视觉上容易混淆的状态：

- 夹爪已闭合但没有夹住物体。
- 夹爪刚好接触物体。
- 夹持力不足、可能打滑。
- 夹持力过大、可能压坏物体。

因此模型不需要仅从手指在图像中的像素距离判断“是否抓住”，而是能使用连续的物理状态。

#### 5. `virtual target` 是显式的柔顺控制标签，不是物体位置标签

本地 UMI-FT 后处理会从平滑后的 tool-frame wrench 生成两个附加标签：

```text
stiffness k
virtual target T_world_virtual
```

它的逻辑是：当力很小，使用高刚度且不引入位移；当力变大，降低刚度，并计算近似位移：

```text
delta_x_tool ~= - wrench_tool / k
T_world_virtual = T_world_tool @ T_tool_delta
```

这把“观测到外力后，理想参考点应在当前工具位姿的哪个方向偏移，以及应该多柔顺”转化为可监督标签。它的好处是，学习策略不只输出刚性位置轨迹，还能学习接触时的目标位置、夹持力和柔顺程度。

这里的 `virtual target` 表示**顺应接触后的控制参考目标**；不要把它和“被抓取物体的绝对位置”混为一谈。

#### 6. 输入输出的因果结构更清楚

一条 UMI-FT 训练样本不是随意拼接字段，而是明确的时间结构：

```text
过去观测窗口:
  RGB / depth / relative pose / gripper / wrench

当前参考 frame:
  最后一帧工具 pose

未来动作窗口:
  相对目标 pose / virtual target / stiffness / gripper / grasp force
```

采样器基于 timestamp 而不是数组下标，确保 RGB、pose、wrench 和 gripper 都落在同一个物理时间窗口。高频 wrench 在需要映射到 robot/action 时间点时，通过最近 timestamp 查找或插值处理。

这比“某一帧图片配某个 CSV 第 i 行动作”的监督关系更可信，也能避免由于不同采样率产生的伪标签。

### 7.8 这种结构降低了什么学习难度

| 原始难题 | UMI/UMI-FT 的数据设计如何降低难度 |
| --- | --- |
| 绝对坐标因场景、机器人 base 和 reset 而变化 | 统一改成当前工具 frame 下的相对 pose |
| 第三人称画面难以对应到末端动作 | 使用腕部/夹爪第一视角，观察与动作共定位 |
| 视觉难以判断是否接触或是否抓牢 | 用左右 wrench、gripper width 和 grasp force 显式提供物理状态 |
| 接触后刚性轨迹容易卡住或损坏物体 | 用 wrench 派生 virtual target 和 stiffness，学习柔顺行为 |
| RGB、depth、force 的采样率不同 | 每路保留独立 timestamp，采样器按时间取样 |
| 换机器人时关节轨迹无法复用 | 采集工具/TCP 层表示，执行端再做 IK 和限幅 |

这正是“数据更容易拟合”的实质：不是模型更聪明，而是训练数据把任务中真正相关的几何关系、接触状态和控制目标以低歧义方式提供给模型。

### 7.9 这套数据结构的边界

上述优势仍依赖几个前提：

- iPhone/SLAM pose 在 episode 内足够稳定。
- CoinFT 的学习式标定没有明显超出覆盖范围。
- sensor frame 到 TCP 的外参和夹爪宽度插值正确。
- 训练和部署的相机视角、工具几何和延迟处理没有发生过大偏移。

如果这些前提被破坏，模型会学到一致但错误的关系。因此 raw 数据、标定文件、时间对齐报告和坐标变换 metadata 必须保留，不能只留下最终 Zarr。

## 8. 从 UMI-FT 到当前项目的继承关系

当前项目不是简单复制官方 UMI-FT，而是继承其核心思想并进行工程扩展。

### 8.1 继承的内容

- 使用手持式 UMI 作为示教接口。
- 不直接绑定某一台机器人关节空间。
- iPhone/工具 pose 作为动作来源。
- 左右 CoinFT 分别记录六维力觉。
- 夹爪宽度以连续值保留。
- 每种模态使用自己的时间戳。
- 最终使用 UMI-FT episode replay-buffer Zarr。

### 8.2 当前项目增加的内容

- 增加 Intel RealSense D435i 固定全局 RGB-D。
- 用全局相机弥补手持相机近距离观察的遮挡问题。
- 笔记本作为统一采集协调器，管理三路设备和录制事件。
- iPhone 通过 USB/usbmux 或实时协议向笔记本传输数据。
- 采集层保留更完整的 raw、normalized、aligned 中间结果。
- 将时间同步、丢帧、预录制、事件和数据质量检查显式写入 metadata。

### 8.3 当前项目为什么仍然选择 iPhone，而不是直接沿用 GoPro

当前选择 iPhone 的工程理由是：

1. 当前需要的不只是 RGB 视频，还需要 Depth、ARKit pose 和内参。
2. iPhone 能在设备侧同时提供这些信息，减少独立追踪器和额外同步设备。
3. 夹爪 marker 和局部操作区域需要在相机中稳定可见，iPhone 安装角度和近景视场更适合这一任务。
4. 当前项目已经围绕 iPhone 的 pose、depth、gripper stream 和笔记本接收链路实现了采集协议。

这不是说 GoPro 不好。GoPro 在原始 UMI 中的优势是广角、IMU 和动态视觉 SLAM；iPhone 的优势是把 RGB、Depth、pose 和相机参数集中在一个更完整的移动计算平台中。

## 9. 当前项目的技术定位

当前项目可以被准确描述为：

> 一个继承 UMI/UMI-FT 本体无关示教思想、采用 iPhone + 双 CoinFT + 全局 RGB-D 相机的多模态数据采集与标准化导出系统。

数据链路为：

```text
iPhone:
  RGB + Depth + ARKit pose + gripper state

CoinFT:
  left/right raw channels -> calibrated 6D wrench

D435i:
  global RGB + Depth

Laptop:
  timestamps -> episode -> alignment -> coordinate transform -> Zarr
```

当前已经具备：

- 本体无关的手持示教采集。
- 多路视觉、位姿、夹爪和力觉记录。
- 时间对齐和坐标变换基础。
- UMI-FT replay-buffer Zarr 导出。

当前尚未完全具备：

- 任意机器人之间自动的末端动作重定向。
- 在线跨本体遥操作。
- 目标机器人 IK、关节限位和碰撞检查的一体化执行模块。
- 所有夹爪类型的统一开合语义映射。

## 10. 汇报中可以采用的硬件选型论证

### 为什么选择 UMI

> 因为我们要规模化收集可迁移的末端操作示教，而不是购买多台机器人去录制各自专属的关节轨迹。UMI 的主体可 3D 打印、是被动机械结构，人可以自然地在真实场景中示教；数据最终使用相对工具轨迹而不是绝对关节角，因此把机器人差异留给部署时的 IK 和安全约束层。

### 为什么选择 iPhone

> 因为 iPhone 是可获得、可开发、可替换的集成传感器平台。它在一个设备里给出 RGB、Depth、ARKit 6DoF 位姿、内参和采集界面，避免我们从零组合相机、深度、IMU、视觉惯性定位、同步和设备端 UI；安装在夹爪上后还能让相机持续看到局部操作区和夹爪 marker。

### 为什么选择 CoinFT

> 因为传统商用六维 F/T 的质量、体积、线缆/供电接口和价格适合装在机器人腕部，却不适合在手持夹爪的两个指端复制部署。CoinFT 单个约 2 g，BOM 约 10 美元，可左右各装一个；它直接读取电容通道变化，再通过每颗传感器的 ONNX 小模型估计六维 wrench。这样我们获得的不只是“有无接触”，还包括左右接触、夹持力和用于柔顺控制的物理反馈。

### 为什么增加 D435i

> 因为腕部视角使视觉和动作天然共坐标，但也会被手和物体遮挡。D435i 提供固定的全局 RGB-D 作为外部上下文；它不替代 iPhone，而是让“局部、动作对齐的视角”和“全局、抗遮挡的视角”同时存在。
